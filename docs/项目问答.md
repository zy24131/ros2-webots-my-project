# 项目问答

## Q1：QoS 模块怎么用、为什么要用

**问题**

> 你的 QoS 模块怎么用的，为啥要用？

**回答**

ROS2 的 pub/sub 必须约定 QoS（可靠性、队列深度等），发布者和订阅者策略不匹配时可能连不上或收不到消息。项目把各端点的 QoS 抽到 `fsm::QoSFromParams()`，创建 publisher/subscriber 时传入即可，默认值写在代码里、精细配置放在 `fsm/config/my_robot.yaml`，改 profile 不用重新编译。控制类话题（`mode`、`steering_command`、`joint_commands`）用 `reliable` 保证不丢；高频流（方向盘、关节状态、轮速）用 `sensor_data` 只取最新，避免旧数据积压——这样既统一各节点写法，又能在仿真/实车间按需调参。

```cpp
create_subscription<...>(topic, fsm::QoSFromParams(this, "qos.steering_input_sub", "sensor_data"), cb);
create_publisher<...>(topic, fsm::QoSFromParams(this, "qos.steering_command_pub", "reliable"));
```

**相关**：`fsm/include/fsm/qos.hpp` · `fsm/config/my_robot.yaml`

## Q2：为什么用状态机和 Trigger

**问题**

> 为啥用状态机和 trigger？

**回答**

平台同时存在窄/宽轮距、切换中、原地自转等多种工况，HMI 通过 Service 下发的只是「意图」（`motion_` 转向还是自转、`track_intent_` 要窄还是宽），并不等于机器人当前处于什么阶段。FSM 用 case 0~5 的显式状态（`narrow_track` / `switch_to_wide` / `wide_track` / `switch_to_narrow` / `spin_left` / `spin_right`）描述**当前真实工况**，再通过 Trigger 把「意图变化 + 当前状态」翻译成**何时迁移、何时发 Action**：例如 Service 只存轮距意图，FSM 发现「当前窄轨、意图要宽轨」才触发 `kTrackRequestWide` 并发起 `SetTrackAction`；自转时先 Cancel 进行中的轮距任务再切到 spin 态。这样意图与执行解耦，下游 `steering_control` 只订阅 `/my_robot/mode` 就能知道该输出转向还是停发，轮距伸缩的长时过程也不会塞进 Service 回调里。

50ms 定时器里固定走 `DetectTrigger()` → `FireTrigger()` → 发布 `mode`，逻辑集中、可打日志、失败可回滚，比在每个 Service 回调里直接改状态更清晰。

```cpp
void Tick() {
  const FsmTrigger t = DetectTrigger();   // 读 motion_/track_intent_/state_ 判条件
  if (t != FsmTrigger::kNone) FireTrigger(t);  // 迁状态、发/取消 Action
  mode_pub_->publish(ModeToString(state_));    // 下游按 mode 选算法
}
```

**相关**：`fsm/src/fsm_node.cpp` · `fsm/include/fsm/motion.hpp`

## Q3：本项目的 ROS2 架构是什么，和 work 有什么区别

**问题**

> 你的 ros2 架构是怎么样子的，和 work 的 ros 架构区别？

**回答**

本项目是 **ROS2 Humble + 分层运动控制栈**，只做「怎么动」这一层：L3 `fsm` 管模式与意图，L2 三个业务节点（`steering_control` / `actuator_control` / `wheel_speed_control`）算控制量，L1 `hardware_bridge` 对接 Webots 或真机 IO。对外用 **Service 存意图**（`set_motion` / `set_track`）、**Action 跑长任务**（轮距伸缩 `SetTrackAction`）、**Topic 传连续量**（方向盘、关节命令、轮速、`mode`）；`actuator_control` 是唯一 `joint_commands` 发布者，和 work 里底盘合并下发的思路一致。多节点 launch 启动，参数集中在 `my_robot.yaml`，算法库 `robot_kinematics` 与 ROS 解耦。

`/home/kemove/Downloads/work`（`study` / `mower_sw`）是 **ROS1 整机业务栈**，范围大得多：一个 `mower_fsm` 进程里挂十几个 Manager 单例（地图、割草、规划、感知、蓝牙、IoV、LCD…），用 **stateless4cpp** 维护几十种 `MowerState`；模块间主要靠 **Topic 成对收发**（如 `planner_set_state` / `planner_update_state`），APP 指令走蓝牙串口而不是 ROS Service。底盘是独立包 `mower_chassis`：UART 收发自 `RosWrapper`，发布 `/ninebot/battery_state`、`/ninebot/cmd_vel` 等大量话题，Action 多用于 RTK 等底盘侧任务。

```text
my_project:  HMI → Service/Action → fsm → mode → L2 控制 → joint_commands → hardware_bridge → Webots
work:        APP/蓝牙 → Manager 群 + GlobalFsm(50+态) → Topic 网状通信 → mower_chassis(UART) → 下位机
```

本质区别：**本项目是 ROS2 多节点、窄域运动中间件，接口按意图/执行/连续流拆开**；**work 是 ROS1 单进程、宽域产品软件，Manager + Topic 织网，底盘 IO 单独一包**。借鉴的是 work 的 FSM + 底盘统一下发模式，但规模、通信选型和 ROS 版本都不同。

**相关**：`docs/架构说明.md` · `docs/ros2_communication.md` · work：`study (副本)/src/main_node.cpp` · `mower_chassis/ros_wrapper.h`

## Q4：哪种架构更好，ROS1 有 master 节点吗

**问题**

> 就是哪种架构好，它的 ros1 有 master 节点吗？

**回答**

没有绝对「哪种更好」，看**要做多大、做多细**。work 那套适合**整机量产软件**：地图、割草、规划、感知、蓝牙、云端都要，模块多、历史包袱大，用 ROS1 单进程 + 一堆 Manager 把业务塞在一起，进程内调用快、联调习惯成熟，但耦合重、难单独测某一层。本项目适合**运动控制中间件 / 仿真验证**：只管窄宽轨、转向、自转，ROS2 多节点边界清楚，Service/Action/Topic 分工明确，换 Webots 或真机只动 L1，学习和答辩都好讲——但如果要把割草、建图、APP 全搬进来，还得像 work 那样再加很多 Manager，不会更「高级」，只是**范围不同**。

ROS1 **有 Master，但不是业务上的「主控节点」**。跑 `roscore` 会起一个 **ROS Master**（名字服务 + 参数服务器），所有节点（`mower_fsm`、`mower_chassis`、planner 等）先连 Master 再互相发现；Master 挂了，Topic/Service 就断了，本身不参与割草或控车逻辑。work 里真正的业务中枢是 **`mower_fsm` 进程**（`GlobalFsm` + 各 Manager），底盘是另一个节点 **`mower_chassis`**，二者是平级节点，都依赖 roscore。ROS2 **没有**这个中心 Master，用 DDS 自动发现，各节点对等，靠 launch 和 QoS 配好即可。

```bash
# ROS1 典型启动（先有 Master，再起业务节点）
roscore                                    # 基础设施 Master，不是 mower_fsm
rosrun mower_fsm mower_fsm                 # 业务大节点
rosrun mower_chassis mowerChassis          # 底盘 IO 节点
```

**相关**：work `study (副本)/src/main_node.cpp`（`ros::init(..., "mower_fsm")`）· 本项目 `ros2 launch fsm my_robot.launch.xml`（无 roscore）

## Q5：DDS、QoS、Launch 都是啥，怎么配合

**问题**

> 就是 DDS 和 QoS，launch 配合都是啥？

**回答**

可以想成三层：**Launch 负责「把节点拉起来、参数灌进去」**；**DDS 负责「节点之间怎么找到对方、怎么传数据」**；**QoS 负责「传的时候按什么规则传」**。ROS1 要靠 `roscore` 当中间人；ROS2 底层直接用 **DDS**（Humble 默认 FastDDS），各节点启动后自动发现同话题的 pub/sub，没有中心 Master。DDS 只管连通和传输，具体「可不可靠、队列多长、要不要持久」由 **QoS** 决定——本项目在代码里用 `fsm::QoSFromParams()` 读参数生成 QoS，yaml 里按端点配 `profile: reliable` 或 `sensor_data`，创建 pub/sub 时带上，两边策略兼容才能通信。

**Launch** 是 ROS2 的启动脚本（本项目 `my_robot.launch.xml` → `control_bringup.launch.xml`），一次拉起 `fsm`、`steering_control`、`actuator_control`、`wheel_speed_control` 四个节点，并用 `<param from="my_robot.yaml"/>` 把同一份参数（含 `qos.*`、死区、超时等）注入各节点；`run_webots.sh` 另起 Webots + `hardware_bridge`，和控制栈分开终端跑。配合关系就是：**Launch 起进程并加载 yaml → 节点里 QoSFromParams 按 yaml 建 pub/sub → DDS 在后台完成发现和收发**；改 QoS 只动 yaml 或 `--ros-args -p qos.xxx:=...`，不用改 Launch，除非要增删节点。

```xml
<!-- control_bringup.launch.xml：起节点 + 灌参数 -->
<node pkg="fsm" exec="fsm_node" name="fsm">
  <param from="$(var params_file)"/>   <!-- 含 qos.mode_pub.profile 等 -->
</node>
```

```yaml
# my_robot.yaml 片段：Launch 灌进来，QoSFromParams 读出去
steering_control:
  ros__parameters:
    qos:
      steering_input_sub: { profile: sensor_data, depth: 10 }
      steering_command_pub: { profile: reliable, depth: 10 }
```

**相关**：`fsm/launch/control_bringup.launch.xml` · `fsm/config/my_robot.yaml` · `fsm/include/fsm/qos.hpp`

## Q6：DDS 底层是什么原理

**问题**

> 就是 DDS 底层啥原理？

**回答**

DDS（Data Distribution Service）可以理解成一块**全局数据总线**：大家不点对点「你连我、我连你」，而是都往同一条逻辑上的「数据空间」里写、从里面读。写的人叫 **DataWriter（发布端）**，读的人叫 **DataReader（订阅端）**，二者通过 **Topic 名 + 类型** 匹配；ROS2 里的 `create_publisher` / `create_subscription` 本质上就是在创建这些 DDS 实体。数据真正上网走的是 **RTPS 协议**（UDP 组播/单播），各进程自己发自己的包，没有 ROS1 那种中心 Master 转发。

节点刚启动时要做 **发现（Discovery）**：先广播「我是谁、在哪个 Domain」，再交换「我有哪些 Topic、QoS 是什么」。双方 QoS 兼容才建立连接——这就是 pub/sub 有时「订阅了却收不到」的底层原因。同一 **Domain ID**（ROS2 默认 `ROS_DOMAIN_ID=0`）内的节点才能互相看见；换 Domain 就等于换一条隔离的总线。传数据时按 QoS 选策略：**Best Effort** 发了就发、可能丢；**Reliable** 有 ACK 和重传；**History depth** 决定缓存几条旧消息；**Durability** 决定晚加入的订阅者能不能拿到历史——本项目 yaml 里的 `reliable` / `sensor_data` 最终都映射成这些 DDS 策略。

和 ROS1 对比：ROS1 是「所有节点向 Master 登记，Master 告诉谁连谁」；DDS 是「各节点自己广播能力，对等发现、对等传输」，更适合多进程、多机，但调试时要自己用 `ros2 topic info -v` 看 QoS 是否匹配。

```text
进程A  DataWriter  ──RTPS(UDP)──┐
                                  ├── 同一 Domain + 同 Topic + QoS 兼容 → 收得到
进程B  DataReader   ──RTPS(UDP)──┘
         ↑
    启动时 SPDP/SEDP 自动发现（无 roscore）
```

**相关**：ROS2 文档 *About DDS* · 本项目 QoS 见 Q1、Q5

## Q7：ROS2 构建 L1~L3 分层运动控制栈是啥

**问题**

> ROS2 构建 L1~L3 分层运动控制栈是啥？

**回答**

这是简历里对本项目架构的概括：**把「怎么动」拆成三层，每层只管一类事，层与层之间用 ROS2 接口连接**。L3 是**决策层** `fsm`：收 HMI 的 Service 意图（转向/自转、窄宽轨），用 Trigger 状态机决定当前处于哪种工况（case 0~5），发布 `/my_robot/mode`，轮距切换时当 Action 客户端；它不算关节角、不碰 Webots。L2 是**控制层**三个节点：`steering_control` 把方向盘 + mode 算成 `steering_command`；`actuator_control` 合并转向命令和 SetTrackAction 插值，**唯一**发布 `joint_commands`，还带 450ms 看门狗；`wheel_speed_control` 发四轮轮速（差速，当前占位）。L1 是**IO 层** `hardware_bridge`：订阅 `joint_commands` / `wheel_speeds`，读 Webots 关节反馈再发 `joint_states`，真机时整包换成阀控/PLC 驱动，L2/L3 **不用改**。

分层的好处是职责清晰、可替换：换仿真/真机只动 L1；加自转 Action 只动 L3 + 部分 L2；算法在 `robot_kinematics` 纯 C++ 库里，L2 调用即可。Launch 也按层组织——`control_bringup.launch.xml` 起 L2/L3，Webots 侧单独起 L1。

```text
L3 fsm          → mode / Service / Action 客户端
L2 控制三节点    → steering_command、joint_commands、wheel_speeds
L1 hardware_bridge → joint_states ↔ Webots/真机
```

**相关**：`docs/架构说明.md` · `docs/steering_flow.md` · `docs/项目简历.md`

## Q8：关节索引 SSOT 是啥

**问题**

> 关节索引 SSOT 是啥？

**回答**

**SSOT**（Single Source of Truth）= **单一数据源**：全项目关节「叫什么名字、数组第几位是谁」只在一个文件里定义，别处只引用、不各自抄一份表。本项目就是 `fsm/include/fsm/joint_config.hpp`。机器人有 8 个转向关节、4 个驱动轮、Webots 里 12 个电机，三套下标**不能混用**：`steering_index` 0~7 对应 `SteeringCommand` / `joint_commands` 的 8 个角（节臂/轮臂交替，见 `kSteeringJoints`）；`wheel_speed_index` 0~3 对应 `WheelSpeeds` 四轮速（见 `kDriveWheels`）；`webots_index` 0~11 是 `hardware_bridge` 按 Webots 模型树遍历 12 个电机的顺序（节臂→轮臂→驱动轮重复四组，见 `kWebotsActuators`），并通过 `wheel_speed_index` 字段把驱动轮和轮速数组对上号。

以前如果 `steering_control`、`actuator_control`、`hardware_bridge` 各写一套 `link_002_joint…`，改 URDF 或顺序错一位就会「算的是 A 关节、下发到 B 关节」。SSOT 之后改关节表只动 `joint_config.hpp`，算法库 `robot_kinematics` 也按同一顺序输出 8 维关节角。

```cpp
// steering_index 2 → link_005_joint（第 3 个转向关节）
cmd.name.push_back(fsm::kSteeringJoints[i].name);

// Webots 第 2 号电机是 link_004_joint，且 wheel_speed_index=0
kWebotsActuators[2]  // → 驱动轮，对应 WheelSpeeds[0]
```

**相关**：`fsm/include/fsm/joint_config.hpp` · `docs/steering_flow.md` §关节索引

## Q9：啥时候用 Service、Action、Topic，用法上有啥区别

**问题**

> 就是啥时候用 service，action topic，而且这几个有啥区别用法上？

**回答**

一句话选型：**Topic 传「一直在变的流」；Service 传「问一句、答一句的指令/查询」；Action 传「要跑一阵、还要进度和结果的任务」**。Topic 是发布-订阅，发出去不等人接，可以 20ms 一直发方向盘、关节命令，订阅者取最新即可，适合 `steering_input`、`steering_command`、`joint_commands`、`mode`。Service 是客户端发 Request、服务端回 Response，**一次调用一次结果**，调用完就结束，适合「改个意图、立刻知道成没成」——本项目 `set_motion` / `set_track` 只把转向/自转/窄宽轨**意图**写进 FSM，马上返回 success，不负责等腿伸到位。Action 在 Service 之上多了 **goal 执行 + 周期性 feedback + 最终 result**，还能 cancel，适合**秒级以上的过程**——轮距伸缩走 `SetTrackAction`，`fsm` 发 goal，`actuator_control` 边插值边报 progress，完成再回调改 FSM 状态；若用 Service 干这个，调用方会阻塞或得自己轮询，接口会很别扭。

用法上：Topic 用 `create_publisher` / `create_subscription`，多对多；Service 用 `create_service` + `ros2 service call`，一对一同步；Action 用 `ActionServer` + `ActionClient`，客户端 `async_send_goal`，服务端在 execute 里循环发 feedback。本项目刻意拆开：**Service 存意图 → FSM 判条件 → Action 执行 → Topic 传连续控制**，避免一种机制包打天下。

```bash
# Service：改意图，立刻返回
ros2 service call /my_robot/set_track my_robot_msgs/srv/SetTrack "{track: 1}"

# Topic：连续发，不阻塞
# steering_input / steering_command / joint_commands / mode

# Action：FSM 内部发起，等 progress + success（HMI 一般不直接 call）
```

| | Topic | Service | Action |
|---|-------|---------|--------|
| 模型 | 发布-订阅，多对多 | 请求-响应，一对一 | 目标-反馈-结果 |
| 是否阻塞 | 否 | 调用方等 Response | 异步，可 cancel |
| 典型场景 | 传感器、控制量、状态广播 | 改模式、查参数 | 导航、机械臂、轮距切换 |
| 本项目例子 | 方向盘、关节命令、mode | set_motion、set_track | SetTrackAction |

**相关**：`docs/ros2_communication.md` · `fsm_node.cpp` · `actuator_control_node.cpp`

## Q10：为什么 `actuator_control` 唯一发 `joint_commands`？多节点同时发会怎样？

**问题**

> 为什么 `actuator_control` 要唯一发 `joint_commands`？多节点同时发会怎样？

**回答**

因为 **`joint_commands` 是最终执行命令**，同一时刻只能有一套来源：`steering_control` 的转向期望、轮距 Action 的插值轨迹、看门狗超时归零——这些必须在**一个节点里仲裁**后再下发。`steering_control` 只发中间量 `steering_command`（语义是「期望姿态」），`actuator_control` 在 20ms 定时器里决定：有 Action 在跑就走 `ExecuteTrackAction()` 插值发令，否则用最新 `steering_command`（超 450ms 则发零位）。这样 L1 `hardware_bridge` 只需订阅一个话题，不用猜该听谁的。

若 **`steering_control` 和 `actuator_control` 甚至 Action 逻辑各发一份 `joint_commands`**，ROS2 Topic 允许多发布者，但 `hardware_bridge` 回调是**整包覆盖**——谁的消息后到谁生效，顺序不确定，可能出现：切轨时腿还在跟方向盘抖、Action 快到位时被 steering 打断、看门狗只对一路生效另一路仍在发令。本质是**争用执行器、无统一仲裁**，仿真里表现为关节抽抖或切换失败，真机上更危险。work 割草机底盘也是「合并后统一下发」，本项目用 `actuator_control` 承担这个角色。

```cpp
void Tick() {
  if (active_goal_) { ExecuteTrackAction(); return; }  // 切轨优先，不用 steering
  PublishFromSteeringCommand();  // 唯一出口 publish joint_commands
}
```

**相关**：`actuator_control_node.cpp` · `hardware_bridge` 的 `JointCommandCallback`（整包覆盖）· `docs/steering_flow.md`
